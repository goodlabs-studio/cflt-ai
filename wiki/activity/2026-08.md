### MCP-validated this pass (2026-08-13)

- Metrics API served from `https://api.telemetry.confluent.cloud/v2/metrics/cloud/...` — **a different host from `api.confluent.cloud`**, which serves resource discovery. Allowlisting only the latter yields a healthy-looking config that never delivers data. This is now the lead finding in both documents.
- API key must be **resource-scoped for resource management**; Confluent states directly that *"API keys resource-scoped for Kafka clusters cause an authentication error."*
- `MetricsViewer` role bound to a **service account** is the authorization requirement. The 401-vs-403 split is diagnostic: 401 = wrong key scope, 403 = missing role.
- Dynatrace extension connects with a resource-scoped key and populates a prebuilt dashboard within minutes of resource selection.
- Packaged integrations lag the Metrics API — documented explicitly for Grafana (*"doesn't include metrics launched after the integration's own last update"*); structurally applies to the Dynatrace extension too.

### Error caught and corrected mid-task

An initial draft of the runbook asserted Dynatrace metric keys in the form `confluent.kafka.server.received_bytes`. **Those keys do not exist.** They were an artifact of a regex matching the *middle* of the CC-native name `io.confluent.kafka.server/received_bytes`. The validated Dynatrace DQL form in `concepts/observability-metrics-mapping.md` is `confluent_kafka_server.received_bytes` — underscored namespace, dot before the metric name. Both documents now lead §5.1 / the naming section with a **discovery query** rather than asserted keys, and tabulate all three conventions (CC-native, Prometheus-flavoured, Dynatrace DQL) side by side.
